# Lab 3-4 — каталог подкастов

Spring Boot REST API хранит каталог подкастов и управляет выпуском эпизодов. Аудиофайл в каталоге — запись с путём, форматом и размером. Слот определяет, когда выпуск разрешено выполнить. Редактор запускает публикацию через API. Spring Security защищает каталог с помощью HTTP Basic и CSRF.

## Предметная модель

| Маршрут CRUD | Данные и связи |
| --- | --- |
| `/api/users` | Профиль с уникальным без учёта регистра email. У автора может быть несколько подкастов. Зарегистрированный профиль связан с учётной записью. |
| `/api/podcasts` | Подкаст одного автора. Состояния `DRAFT`, `ACTIVE`, `ARCHIVED`. |
| `/api/episodes` | Эпизод одного подкаста с положительной длительностью. Состояния `DRAFT`, `PUBLISHED`, `UNPUBLISHED`. |
| `/api/audio-files` | Аудиоверсия одного эпизода с положительным размером. Один файл эпизода может быть основным. |
| `/api/publication-slots` | Время и состояние выпуска эпизода. Составной внешний ключ гарантирует принадлежность эпизода указанному подкасту. Состояния `SCHEDULED`, `PUBLISHED`, `CANCELLED`, `WITHDRAWN`. |

Все ресурсы поддерживают `GET` списка, `GET /{id}`, `POST`, `PATCH /{id}` и `DELETE /{id}`. Создание возвращает `201` с заголовком `Location`, удаление — `204`. Удаление автора, подкаста или эпизода каскадно удаляет связанные записи. Время слота хранится как момент времени, а API возвращает его в UTC.

## Бизнес-операции

Все маршруты ниже используют `POST`.

| Маршрут | Правило и результат |
| --- | --- |
| `/api/episodes/{id}/schedule` | Тело `{"scheduledAt":"<ISO 8601 с UTC-смещением>"}`. Для неопубликованного эпизода активного подкаста с основным аудио создаёт слот на будущее. У эпизода может быть один ожидающий слот, у подкаста — один ожидающий выпуск на данный момент времени. |
| `/api/publication-slots/{id}/publish` | Когда время ожидающего слота наступило, повторно проверяет статус подкаста, эпизода и наличие основного аудио. Переводит эпизод и слот в `PUBLISHED` за одну транзакцию. |
| `/api/episodes/{id}/withdraw` | Снимает опубликованный эпизод. Эпизод становится `UNPUBLISHED`, слот сохраняется в истории со статусом `WITHDRAWN`. После снятия эпизод можно выпустить заново через новый слот. |
| `/api/episodes/{id}/switch-primary` | Тело `{"audioFileId":42}`. Заменяет имеющийся основной файл другим файлом того же эпизода, сохраняя обе версии. Повторный выбор уже основного файла возвращает его. |
| `/api/podcasts/{id}/archive` | Архивирует активный подкаст, снимает его опубликованные эпизоды и отмечает выпущенные слоты как `WITHDRAWN`. Ожидающие слоты становятся `CANCELLED`. Возвращает число снятых эпизодов и отменённых слотов. |

CRUD слотов позволяет вручную регистрировать и менять время ожидающего выпуска, в том числе указывать уже наступившее время. Опубликовать или снять выпуск можно через соответствующие операции. Пока эпизод опубликован, удалить, перенести или снять признак с его основного файла можно только после снятия эпизода. Для замены файла используйте `switch-primary`. Активный подкаст с опубликованными эпизодами или ожидающими слотами закрывается через `archive`.

Некорректный ввод возвращает `400`, отсутствующая запись — `404`, конфликт состояния или ограничений целостности — `409`. PostgreSQL проверяет внешние ключи, обязательные поля, допустимые статусы, уникальность email, основного файла и слотов. Изменения через REST выполняются в транзакциях с общей блокировкой записи на уровне PostgreSQL. Это последовательно выполняет проверки и запись даже при параллельных запросах к нескольким экземплярам API.

## Аутентификация и права

1. Выполните `GET /api/auth/csrf`. Ответ содержит `headerName` и `token`, а сервер устанавливает cookie `JSESSIONID`.
2. Для регистрации выполните `POST /api/auth/register` с JSON `{"name":"Анна","email":"anna@example.test","password":"<надёжный пароль>"}`. Передайте ту же cookie и CSRF-токен в заголовке из `headerName`. Регистрация создаёт профиль и учётную запись с ролью `READER` в одной транзакции.
3. В защищённых запросах используйте HTTP Basic с email и паролем. `GET /api/auth/me` возвращает ID, email и роль. Для каждого `POST`, `PATCH` и `DELETE` передавайте cookie и CSRF-заголовок. После окончания сессии получите новый токен.

Логин проверяется без учёта регистра. Пароль должен содержать минимум 12 символов, включая заглавную и строчную буквы, цифру и специальный символ. Максимум — 72 байта UTF-8. Таблица `accounts` хранит только BCrypt-хеш пароля, роль и признак активности. При удалении профиля его учётная запись удаляется каскадно. Cookie хранит идентификатор сессии CSRF. Сервер заново проверяет Basic Auth и состояние учётной записи на каждом защищённом запросе.

| Роль | Доступ |
| --- | --- |
| `READER` | Чтение общего каталога подкастов, эпизодов, аудиофайлов и слотов, включая редакционные состояния. |
| `EDITOR` | Права читателя, создание и изменение записей общего каталога, удаление записей и пять операций выпуска. |
| `ADMIN` | Права редактора, CRUD профилей и `PATCH /api/users/{id}/access` с JSON `{"role":"EDITOR","enabled":true}`. Можно менять роль между `READER` и `EDITOR` и отключать эти учётные записи. Администратор защищён от собственного удаления и отключения. |

`401 AUTHENTICATION_REQUIRED` означает отсутствие действительных учётных данных, в том числе при отключённой записи. `403 ACCESS_DENIED` означает запрет по правам, `403 CSRF_INVALID` — отсутствующий или недействительный CSRF-токен. Защита CSRF проверяет изменение до проверки полномочий. При действительных учётных данных и CSRF-токене бизнес-конфликт по-прежнему возвращает `409`.

## Запуск на Windows

Нужны JDK 17 или новее и PostgreSQL. На компьютере, где выполнялось задание, база уже создана на `127.0.0.1:55432`, а `.env` содержит подключение к базе и локальную учётную запись администратора. Из каталога проекта выполните в PowerShell:

```powershell
.\build.cmd
.\start.cmd
```

API доступен на `http://localhost:8080`. `build.cmd` собирает приложение через Maven Wrapper и запускает интеграционные тесты против настроенной базы. Тесты используют администратора из `.env`, создают свои записи и удаляют их в конце.

Для новой установки создайте базу один раз с помощью `psql` от имени администратора PostgreSQL. Команды ниже используют стандартный порт `5432`. Выберите отдельный пароль для приложения.

```powershell
Copy-Item .env.example .env
$env:PODCAST_APP_PASSWORD = Read-Host 'Пароль для podcast_app' -MaskInput
psql -X -h 127.0.0.1 -p 5432 -U postgres -d postgres -f db/init.sql
Remove-Item Env:PODCAST_APP_PASSWORD
```

В `.env` укажите тот же пароль в `DB_PASSWORD` и фактический порт в `DB_URL`. Задайте `ADMIN_EMAIL` и надёжный `ADMIN_PASSWORD` до первой сборки. При запуске приложение создаёт администратора, если в базе его ещё нет. Изменение значений в `.env` после создания администратора не меняет его учётную запись. Git игнорирует `.env`.

`db/init.sql` создаёт роль `podcast_app` и базу, выполняет `db/schema.sql`, `db/seed.sql` и `db/security.sql`. Для уже существующей базы задания 3 примените от имени администратора PostgreSQL только обновление схемы безопасности. Укажите фактический порт своей базы:

```powershell
psql -X -v ON_ERROR_STOP=1 -1 -h 127.0.0.1 -p 55432 -U postgres -d podcast_catalog -f db/security.sql
```

Роль приложения может читать и менять строки каталога. Для `accounts` разрешены чтение, вставка и изменение роли и активности. Схемой управляет администратор PostgreSQL.

Для повторного запуска локального экземпляра PostgreSQL после перезагрузки компьютера из каталога проекта выполните:

```powershell
& ..\..\work\postgres\bin\pg_ctl.exe -D ..\..\work\postgres-data -l ..\..\work\postgres.log -w start
```

## Проверка в Postman

Импортируйте [коллекцию](podcast-catalog.postman_collection.json). В локальном окружении Postman задайте `adminEmail` и `adminPassword` из `ADMIN_EMAIL` и `ADMIN_PASSWORD` в `.env`. Запустите коллекцию целиком через **Collection Runner** с включённым cookie jar.

Сценарий получает CSRF-токен, проверяет регистрацию и отказы, входит как читатель, отключает и включает учётную запись от имени администратора и выполняет операции каталога от имени редактора. Для демонстрации выпуска без ожидания сценарий переносит ожидающий слот на уже наступившее время через `PATCH`. Созданные записи удаляются в конце, а демонстрационные данные из `db/seed.sql` остаются в базе.
